# Polydispute — Data Architecture & Research Notes

## Project Goal

Join three data streams for Polymarket disputed markets:

1. **Polymarket market data** — prices, volumes, question metadata (Gamma API)
2. **UMA dispute resolution data** — who disputed, DVM vote breakdowns, slashing outcomes
3. **Discord thread signals** — community discussion sentiment around disputed votes

The end goal: a unified dataset linking market IDs → disputes → vote outcomes → discussion threads, enabling analysis of how disputes are resolved and whether discord signals predict vote outcomes.

---

## System Architecture

### End-to-End Data Flow

```
Polymarket Gamma API (off-chain)
    │
    │  questionID (hex)
    ▼
UmaCtfAdapter (Polygon contract)
    │  call getQuestion(questionID)
    │
    │  ancillaryData (raw bytes — market rules)
    ▼
Managed Optimistic Oracle V2 [MOOv2] (Polygon)
    │  Subgraph: polygon-managed-optimistic-oracle-v2
    │  Query: optimisticPriceRequests(where: { ancillaryData })
    │
    │  identifier ("YES_OR_NO_QUERY"), time (unix timestamp)
    ▼
UMA DVM Voting (Ethereum Mainnet)
    │  Subgraph: mainnet-voting-v2
    │  Step 1: Paginate priceRequests → match (identifier, time)
    │  Step 2: Use resolvedPriceRequestIndex for detail query
    │
    │  Vote breakdown: groups, participation, per-address reveals
    ▼
Discord Threads (vote.uma.xyz cron)
    │  Thread ID mapped by: {title}-{timestamp}
    │  Messages cached in Redis, AI summaries generated
    ▼
┌─────────────────────────────────────┐
│         UNIFIED DATASET             │
│  market ↔ dispute ↔ vote ↔ discord  │
└─────────────────────────────────────┘
```

### Three-Source Join Strategy

The unified dataset requires strict primary keys across three disparate sources:

#### Source A: Polymarket (off-chain)
- **Data**: Market ID, raw question text, resolution criteria, trading volume, UmaCtfAdapter address
- **Primary key out**: `ancillaryData` hex string (extracted via `getQuestion(questionID)` on the adapter contract)

#### Source B: UMA On-Chain (Polygon → Ethereum)
- **Data**: Dispute lifecycle, DVM vote breakdowns (voters, weights, outcomes, slashing)
- **Join from A**: Use `ancillaryData` to query MOOv2 subgraph → get `(identifier, time)` → match in DVM VotingV2 subgraph → get `resolvedPriceRequestIndex` → fetch full vote detail
- **Hashing trap**: ancillaryData is keccak256-hashed when bridging Polygon→Mainnet, so raw string matching fails. Must hash locally or match by `identifier`+`time`.

#### Source C: Discord (social signal)
- **Data**: Community discussion, trader arguments, evidence links, dispute coordination
- **Join from A**: Discord threads for Polymarket disputes are tagged/titled with the question text or Market ID. The vote.uma.xyz cron maps threads using `{title}-{timestamp}` keys (spaces removed).

| Hop | Join Key |
|-----|----------|
| Gamma API → UmaCtfAdapter | `questionID` (keccak256 hash) |
| UmaCtfAdapter → MOOv2 subgraph | `ancillaryData` (hex bytes) |
| MOOv2 → DVM subgraph | `identifier` + `time` |
| DVM subgraph → Discord | `{title}-{timestamp}` or Market ID |

## How vote.uma.xyz Works (Reverse-Engineered)

The voter-dapp-v2 uses a **two-stage lazy-load pattern**:

### Stage 1: Paginated lightweight fetch (on page load)

Paginates through ALL resolved priceRequests. No vote breakdown data — just metadata.

```graphql
query getPastVotesLight($skip: Int!, $limit: Int!) {
  priceRequests(
    first: $limit
    skip: $skip
    where: { isResolved: true }
    orderBy: resolvedPriceRequestIndex
    orderDirection: desc
  ) {
    identifier { id }
    price
    time
    ancillaryData
    resolvedPriceRequestIndex
    isGovernance
    rollCount
  }
}
```

Variables: `{ "skip": 0, "limit": 200 }`, then `skip: 200`, etc.

The `participation` fields are set to **placeholder zeros** in the frontend code (`getPastVotes.ts:113-121`).

### Stage 2: Detail fetch (on panel expand)

When you click a past vote to expand it, `VotePanelWithLazyLoad.tsx` checks:
- `participation.totalTokensVotedWith === 0` AND `resolvedPriceRequestIndex !== undefined`

If true → fires `getVoteDetails` by the `resolvedPriceRequestIndex`:

```graphql
query getVoteDetails($index: Int!, $latestRoundLimit: Int!) {
  priceRequests(where: { resolvedPriceRequestIndex: $index }) {
    identifier { id }
    price
    time
    ancillaryData
    resolvedPriceRequestIndex
    isGovernance
    rollCount
    latestRound {
      totalVotesRevealed
      totalTokensCommitted
      minAgreementRequirement
      minParticipationRequirement
      groups(first: $latestRoundLimit) {
        price
        totalVoteAmount
        won
      }
      committedVotes(first: $latestRoundLimit) { id }
      revealedVotes(first: $latestRoundLimit) {
        id
        voter { address }
        price
      }
    }
  }
}
```

Variables: `{ "index": 260, "latestRoundLimit": 1000 }`

### For active (unresolved) votes

Single non-paginated query for all `isResolved: false`. Includes full `latestRound.groups` in one shot — this is the live tally during commit/reveal phases.

```graphql
{
  priceRequests(
    where: { isResolved: false }
    orderBy: resolvedPriceRequestIndex
    orderDirection: desc
  ) {
    identifier { id }
    price
    time
    ancillaryData
    resolvedPriceRequestIndex
    isGovernance
    rollCount
    latestRound {
      totalVotesRevealed
      minAgreementRequirement
      minParticipationRequirement
      totalTokensCommitted
      groups { price, totalVoteAmount, won }
      committedVotes(first: 1000) { id }
      revealedVotes(first: 1000) {
        id
        voter { address }
        price
        numTokens
      }
    }
  }
}
```

## AncillaryData Hashing: Polygon → Mainnet

When a dispute escalates from Polygon MOOv2 to Ethereum DVM, the ancillaryData is **not passed verbatim**. It's hashed.

On the Polygon MOOv2 subgraph, you get the raw ancillaryData (the full market rules text as hex).

On the Ethereum DVM VotingV2 subgraph, the ancillaryData field contains a **compressed form**:

```
ancillaryDataHash:<keccak256_of_original>,childBlockNumber:<block>,childOracle:<address>,childRequester:<address>,childChainId:137
```

Example (unhexed):
```
ancillaryDataHash:79ecfe3c17710e92c55206e5b3a042f156f337bd7965b8d417925353c124856b,childBlockNumber:84606522,childOracle:ac60353a54873c446101216829a6a98cdbbc3f3d,childRequester:2c0367a9db231ddebd88a94b4f6461a6e47c58b1,childChainId:137
```

This means **you cannot join Polygon ↔ Mainnet by raw ancillaryData string match**. You must either:
1. Compute `keccak256(polygon_ancillaryData)` and match the hash prefix, OR
2. Match by `identifier` + `time` (which are the same on both sides)

The `eth_scan.py` script handles this by checking both raw bytes and the `ancillaryDataHash:` prefixed form.

## VotingV2 Subgraph Schema (Key Entities)

Source: `reference/subgraphs/packages/votingV2/schema.graphql`

### PriceRequest
- **ID**: `identifier-time-keccak256(ancillaryData)` (constructed in mapping code)
- Core: `isResolved`, `price`, `rollCount`, `time`, `ancillaryData`
- Relations: `latestRound` → `PriceRequestRound`, `committedVotes`, `revealedVotes`
- `resolvedPriceRequestIndex` — monotonic integer, used as the detail query key

### PriceRequestRound
- `totalVotesRevealed`, `totalTokensCommitted`, `votersAmount`
- `minAgreementRequirement`, `minParticipationRequirement` — quorum thresholds
- `groups` → `VoterGroup[]` — the vote breakdown by price
- `winnerGroup` → the winning VoterGroup

### VoterGroup
- `price` — the vote value (0 = No, 1e18 = Yes, 5e17 = Unknown)
- `totalVoteAmount` — total tokens voting this price
- `won` — boolean

### RevealedVote
- `voter` → `User`, `price`, `numTokens`, `group` → `VoterGroup`

### SlashingTracker
- `wrongVoteSlashPerToken`, `noVoteSlashPerToken`, `totalSlashed`

      winnerGroup {
        id
        price

## Engineering Heuristics (Failure Points)

### Dynamic ABI Fetching
Hardcoding the UMA event ABI causes signature mismatches due to contract upgrades (e.g., `uint32` vs `uint256` parameter changes). Fetch the verified ABI dynamically from Etherscan V2 API.

### RPC Pagination
Public RPC nodes throw HTTP 500 if `eth_getLogs` spans too many blocks. Chunk into 500-block steps with retry/backoff.

### Cryptographic Log Filtering
The DVM processes multiple `YES_OR_NO_QUERY` requests simultaneously. Filtering `VoteRevealed` events solely by timestamp returns data from unrelated markets. Must strictly filter by both `identifier` AND `ancillaryData` (or its hash).

### Subgraph Instability & Deprecation
The legacy Voting V1 infrastructure and The Graph Hosted Service are **deprecated**. Attempting to query old `mainnet-voting` slugs returns dead endpoints. The Goldsky endpoints discovered here are the current production URLs as of April 2026, but may change — the voter-dapp-v2 repo does not hardcode them (they're Vercel env vars). The decentralized Graph Network deployment (`5YVXjj28Lv4eLhHg54R1QWVHNn8VAjZnT3vJgEtuyWmY`) is a more stable alternative but requires an API key.

### Cross-Chain Hashing Trap
Scripts that attempt to filter Ethereum Mainnet logs or subgraph data using the raw unhashed Polygon ancillaryData text will **fail silently**. The ancillaryData is compressed into a Keccak-256 hash (`ancillaryDataHash:...`) before bridging L2→L1. You must either hash the payload yourself or match by `identifier`+`time` instead.
